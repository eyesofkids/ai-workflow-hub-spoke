# find-holes — 找漏洞 spoke 派工

你是 hub。本 skill 把規劃書的指定範圍派給乾淨視角的 sub-agent 找漏洞。**spoke 產出意見，不產裁決；採不採用由使用者決定。**

## 步驟

1. **讀規劃書**（參數指定的檔案）。若使用者有指定聚焦章節／問題，只取該範圍；否則取設計定案章節（跳過背景、前情、已定案事實引用）。
2. **組 need-to-know 工單**，內容只有三樣：
   - **待審段落原文**（直接內嵌到 prompt，不給檔案路徑）
   - **前提清單**（標明「前提，不受審」）：規劃書開頭的使用者已定案決策、已驗事實的結論（只給結論一行，不給 facts 檔）
   - **具體問題**（每個 spoke 2–4 條，如「§3.2 的配對規則在併發下有沒有洞？」）
   - **禁止內容**：歷史版本鏈、已廢棄規劃文件、決策過程背景、任何 `_docs` 路徑。先例只能以一行判準形式給（「給尺不給屍」，見 AGENTS.md 出處三規則）。
3. **提出派工計畫，停下等確認**：依規劃內容從三個 lens agent 中選（全部唯讀）：
   - `hole-finder-feasibility`（sonnet）：可行性、可實作性、引用即驗證
   - `hole-finder-safety`（opus）：併發競態、失敗態、輸入驗證、資料洩漏
   - `hole-finder-cost`（sonnet）：計費呼叫閘門順序、pre-check、超限行為

   三種 lens 都不合的規劃書，改用通用 `hole-finder`（sonnet），由你在 prompt 中指定自訂 lens。派工前**必須**先向使用者列出計畫並**明確詢問、停下等確認,未獲同意不得呼叫 Agent**：
   - 派幾個（1–3）
   - 各自的 agent 與 lens
   - 各自的模型（用 agent 預設；若該次的洞需要更深推理，可在 Agent 呼叫以 `model` 參數覆蓋升級 opus／fable,說明理由）
   - 工單內容摘要（給了哪些段落、哪些前提、哪些問題）
   **外派模式（可選）**：需要非 Anthropic 模型的異質視角時，確認後不呼叫 Agent，改為輸出一段可整段複製的自包含工單文字——除上述工單內容外，另含角色定義、`_docs/` 禁令、輸出格式、四項禁止、固定收尾句，以及要派的 spoke——**必須明確寫出 agent 名稱**（`hole-finder-feasibility`／`hole-finder-safety`／`hole-finder-cost`，兩端同名）與數量，不得只給 lens 描述讓 broker 自行對應。由使用者貼進 VSCode 的 `dispatch-broker` 對話窗執行，再把回收結果貼回來。工單實質內容與內派完全相同，差別只在誰執行、跑在哪家模型上。

   使用者對數量／模型／lens 的修改一律照辦。確認後才派,每個 prompt 必含：
   - 工單內容（第 2 步）
   - 允許讀的程式碼檔案清單（僅與待審段落直接相關者）；明令**不得**瀏覽 `_docs/` 下的其他文件
   - 產出格式：「觀察＋依據（檔案:行號或推理）」的清單；**不得**給結論裁決、嚴重度分級、「應該改成」的替代設計、採用建議；不確定的寫成問題不寫成缺陷
4. **回收：先原文、後融合**：每個 spoke 的回報**逐個原文照登**（標明 lens 與模型，不得刪節、改寫或只給總結——使用者必須看得到每個 spoke 各自說了什麼）；之後**另立「hub 判讀」一節**，去重並逐條標註你依脈絡的初步判讀（「成立／不成立＋為什麼／需使用者裁決」）。外派回來的結果走同一套：broker 的稽核表併進原文區一併照登，不得只取結論。
5. **使用者裁決後**，被採納的項目由你修訂規劃書（新版只寫差異）。spoke 的產出永遠不直接成為文件版本。

## 紅線

- spoke 意見不得觸碰「做不做」；若 spoke 越權寫出終止／阻擋類結論，丟棄該結論、只保留其事實部分，並在回報中註明。
- 不得因 spoke 意見自行改規劃書狀態欄。
